# React Native app on the Windows emulator (driven from WSL)

## Overview

An Expo development build is a native shell plus JS served by Metro. Verifying a change means: a shell
built from the current commit, JS from the topic worktree, and — when the point is an API state — a local
stub the app talks to instead of the real backend. Everything runs from WSL except the emulator, which is a
Windows process reachable only through Windows `adb.exe`.

## When to Use

- A change needs live evidence: rendered copy, an error alert, a screen reached by navigation.
- A UI state depends on a response that is hard or destructive to produce for real (declines, 409s, quota
  errors) — inject it.
- NOT for web portals and not as a substitute for the repo's jest suite. Note the repo's package manager:
  with a **pnpm** tree packages sit under `node_modules/.pnpm/@react-native+...`, `transformIgnorePatterns`
  cannot match them, and jest fails before a single test runs. Install with **npm** when the repo ships a
  `package-lock.json`.

## Environment facts that bite

| Thing | Reality |
| --- | --- |
| AVD location | `ANDROID_AVD_HOME` decides it (often `D:\Android\.android\avd`); `%USERPROFILE%\.android\avd` can be empty. `emulator -list-avds` is the authority |
| Device access | only Windows `adb.exe` sees the emulator; the WSL `adb` does not |
| Build | the Windows project's own docs may say "build on Windows", but a WSL SDK (`~/android-sdk`: platforms, build-tools, NDK, cmake, warm `~/.gradle`) builds fine and is faster to script |
| Cleartext | debug manifests usually set `usesCleartextTraffic="true"`, so plain-HTTP stubs work in debug builds only |
| Device CLI | the official `android` CLI (`<android user home>\bin\android-cli.exe`) beats hand-rolled adb for reading and driving the UI. Its AVD commands read **`ANDROID_USER_HOME`**, not `ANDROID_AVD_HOME` — without it `emulator list`/`start` answer "Device … doesn't exist" and exit 0 |
| Type-check | `expo-env.d.ts` is gitignored and generated by `expo start`; a local `tsc` pass is not CI truth. Check with `git archive` + the same `node_modules` |

## Workflow

1. **Identify the shell.** `grep -n 'applicationId\|versionCode' android/app/build.gradle` gives the bundle id
   and the shell version; `adb.exe shell dumpsys package <bundleId> | grep versionCode` gives the installed
   one. A shell older than the JS loads the bundle and then crashes (`Property 'MessageQueue' doesn't exist`
   after an SDK bump). Mismatch ⇒ rebuild. A stale shell is the most common cause of confusing results.
1. **Build in WSL.**
   ```bash
   cd <worktree>/android
   printf 'sdk.dir=%s\n' "$HOME/android-sdk" > local.properties   # gitignored
   ANDROID_HOME=$HOME/android-sdk ./gradlew app:assembleDebug \
     -x lint -x test --no-configure-on-demand -PreactNativeArchitectures=x86_64
   ```
   ~6 minutes warm. Do not use `expo run:android` on Windows and do not add ABIs.
1. **Install through Windows adb.** Copy the APK to `/mnt/d/...`, then
   `adb.exe install -r "D:\...\app-debug.apk"`. Or let the CLI do install + launch in one step:
   `android run --apks 'D:\...\app-debug.apk'` — it picks the single launcher activity itself.
1. **Serve JS.** Metro in WSL (`npx expo start --clear --port 8081`), then
   `adb.exe reverse tcp:8081 tcp:8081` (plus each stub port). Prove the chain before blaming the app:
   `curl localhost:8081/status` from **Windows** must print `packager-status:running`.
1. **Confirm which bundle is running.** Launch the activity, tap the dev-server row, then
   `adb.exe exec-out run-as <bundleId> cat files/DevLauncherApp-BridgelessReactNativeDevBundle.js | grep <marker>`
   with a marker you just changed. A "recently opened" entry can replay the previous Metro's bundle — that is
   how an env change silently fails to apply.
1. **Drive the UI with `android layout`, not with arithmetic.** It returns JSON with `text`, `center`
   (`"[894,1306]"`, ready to tap), `interactions` and `resource-id`; `-d` returns only what changed since
   the last dump, which is how you wait for a transition. Console printing mangles non-ASCII, so always
   write to a file and read that:
   ```bash
   android layout -p -o 'D:\tmp\layout.json'      # read text + center from WSL
   adb.exe shell input tap 894 1306
   ```
   `android screen capture -a -o D:\tmp\s.png` draws numbered boxes; `android screen resolve
   --screenshot D:\tmp\s.png --string "tap #3"` turns a label into coordinates. Fall back to
   `adb.exe shell uiautomator dump /sdcard/ui.xml` when the CLI is unavailable. Screenshots are evidence,
   not a way to read text.
1. **Inject a response** (below), re-run the same screen per state, capture each one.
1. **Restore.** `git restore` the env file, stop Metro and the stub. `pm clear` wipes the login — only when a
   stale bundle genuinely cannot be evicted otherwise.

## Injecting backend states

Point the one base URL at a local stub through the app's env file (usually `env.json`, tracked — restore it
afterwards), then run the stub in WSL:

```js
// /tmp/stub.mjs — forward everything upstream, rewrite one endpoint
http.createServer((req, res) => {
  if (req.method === 'POST' && req.url.startsWith('/some/endpoint')) {
    res.writeHead(422, { 'Content-Type': 'application/json' });
    res.end(JSON.stringify({ status: 422, detail: 'SENTINEL-backend-english', someCode: '1001' }));
    return;
  }
  const up = https.request({ hostname: 'api.example.dev', path: req.url, method: req.method,
    headers: { ...req.headers, host: 'api.example.dev' } }, (r) => {
    res.writeHead(r.statusCode, r.headers); r.pipe(res);
  });
  req.pipe(up);
}).listen(8799);
```

- Set the base URL to `http://10.0.2.2:8799`; `10.0.2.2` is the Windows host and reaches WSL.
- Drive states from a file the stub reads per request (`echo 1001 > /tmp/mode`), so one app session covers
  every case.
- Put a **sentinel** in the field that must not reach the screen; its absence is the assertion, a screenshot
  alone cannot prove it.
- A stub that logs every request is also the fastest way to prove which path the app took — the log tells you
  whether the app called you at all.

Before writing automation for an Android behaviour, check Google's own registry:
`android skills find <keyword>` / `android skills list` — some platform tasks (CameraX, billing, intents,
Compose performance) already ship as an official skill.

## Common Mistakes

| Symptom | Cause / fix |
| --- | --- |
| `Property 'MessageQueue' doesn't exist` | JS newer than the installed shell — rebuild, do not poke the JS |
| Stub sees nothing although the bundle contains its URL | the app runs the previous cached bundle — reload from the dev server, re-check with `grep <marker>` |
| 401s after reload with a fresh JS session | the token lives in `expo-secure-store`, which survives reload — sign in again |
| `input text 'Pass!'` lands as `Pass%21` | adb does not decode it; type characters literally, or use a password without `!`/`&`/`$` |
| Taps stop registering mid-flow | an alert is still up. `android layout` gives the current button's `center`; a coordinate from the previous screen does not |
| `android emulator list/start` says "Device … doesn't exist" and exits 0 | its AVD commands read `ANDROID_USER_HOME`, not `ANDROID_AVD_HOME`; set it for the call, or use `emulator.exe -avd <name>` |
| CLI complains `Specified output directory 'D:\tmp' does not exist` | its paths are Windows paths and it never creates the directory |
| A behaviour cannot be reached at all | a feature flag gates the screen (company/account mode); confirm the flag before mocking anything |
